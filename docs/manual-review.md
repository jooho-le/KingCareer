# 사용자 확인 목록

다섯 직업 현장 체험·수료 카드·Excalidraw 작업실 확인 순서는 [로컬 개발 확인 항목](local-fieldwork.md#사용자-확인-항목)에 추가했습니다. 이번 변경도 테스트 작성·실행 없이 전달합니다.

이번 개편에서는 요청에 따라 테스트를 새로 작성하거나 실행하지 않았습니다. 아래는 사용자가 실행 후 확인할 목록이며 통과 기록이 아닙니다. 실제 모델 호출 경로도 검증하지 않았습니다.

## 준비

[README 실행 방법](../README.md#windows에서-실행)에 따라 FastAPI와 Vite를 실행합니다. 기본 AI 설정은 `template`으로 유지합니다. 서로 다른 학생 두 명을 확인하려면 일반 창과 시크릿 창처럼 쿠키가 분리되는 브라우저 컨텍스트를 사용합니다. 같은 브라우저의 두 탭은 같은 로그인 세션을 사용합니다.

## 화면과 원본

| 확인 | 기대하는 결과 |
| --- | --- |
| `/`에서 원본 소개 페이지 비교 | 6면 큐브의 모양·색·회전·스크롤 연결, 고정 문장, 직업 트랙, 체험·지도·지역 순서 유지 |
| 소개 페이지 체험 후 학생 포트폴리오 확인 | 공개 체험 결과가 학생 기록에 추가되지 않음; 수치는 예시 표시 |
| 시작하기·직업 체험·지도·지역 링크 | 알맞은 `/app/` 화면과 선택한 직업으로 이동 |
| 기존 `/#diagnosis` 북마크 | `/app/#diagnosis`로 연결 |
| 작은 모바일·태블릿·데스크톱 | 본문·선택지·버튼이 가로로 잘리지 않으며 메뉴 사용 가능 |
| 시스템 움직임 줄이기 | 장식 회전·이동이 멈추고 소개·직업 트랙의 모든 내용을 읽을 수 있음 |
| 브랜드·메뉴 | KingCareer 이름과 제공 이미지 사용; 학생 앱에 새 그라데이션·교사 메뉴 없음 |

## 계정과 저장

1. 학생 A를 가입하고 프로필·관심분야·관심 직업을 저장합니다. 로그아웃·재로그인 후 같은 기록이 보이는지 확인합니다.
2. 별도 브라우저의 학생 B에게 A의 지도·초안·체험·포트폴리오가 보이지 않는지 확인합니다. A의 체험 ID를 B의 세션으로 조회하면 404여야 합니다.
3. 비밀번호를 변경하면 다른 브라우저의 이전 세션은 만료되고 현재 창은 새 세션으로 유지되어야 합니다.
4. 학습 기록 삭제는 프로필·저장 직업을 유지하고 진단·체험·프로젝트·체크포인트를 제거해야 합니다. 계정 삭제는 비밀번호 확인 후 로그인과 본인 데이터 접근을 막아야 합니다.
5. 기존 `itda-career-v1` localStorage 값이 자동으로 가져와지거나 삭제되지 않는지 확인합니다.

## 직무체험과 프로젝트

| 확인 | 기대하는 결과 |
| --- | --- |
| 같은 직업의 진행 중 체험 다시 열기 | 마지막으로 저장한 상황·선택·결과부터 이어하기 |
| 체험 중 새로고침·서버 재시작 | 확정된 단계와 응답 복원 |
| 선택·자유 답변 | 서버 결과를 보여준 뒤에만 다음 상황으로 진행 |
| 상황에 질문 | 질문·안내 저장, 현재 단계 유지 |
| 회고·관심도 저장 | 완료 기록 생성; 관심도 감소도 그대로 반영 |
| 완료 후 다시 체험 | 새 세션 생성, 이전 완료 기록 유지 |
| 프로젝트 입력·줄바꿈·공백 | 입력 그대로 초안에 저장, 재접속 후 복원 |
| 프로젝트 수정 이력 | 저장 버전별 답변과 시각 표시 |
| 자동 저장 중 추가 입력 | 요청이 순서대로 저장되고 가장 마지막 입력이 남음 |
| 서버를 끈 상태에서 입력·페이지 이동 | 저장 완료 표시 금지, 오류·재시도 제공, 미저장 입력을 유지 |
| 같은 학생의 두 탭에서 동일 초안 수정 | 충돌을 알리고 입력 보존; 최신 버전 확인 후 의도한 내용 저장 |
| 프로젝트 제출·포트폴리오 다운로드 | 저장한 세 미션 결과물이 본인 활동·UTF-8 텍스트에 포함 |

개발자 도구의 네트워크 기록 또는 `/docs`를 이용해 동일 `clientRequestId`와 동일 본문을 재전송합니다. 새 활동·근거가 추가되지 않아야 합니다. 같은 ID로 다른 본문을 보내거나 새로운 요청에 오래된 `expectedVersion`을 보내면 409여야 합니다. 같은 프로젝트 버전을 다른 요청 ID로 다시 제출해도 같은 활동을 반환해야 합니다.

## 해석과 AI 상태

- 진단 응답만으로 실제 활동 충족률이 올라가지 않아야 합니다. 자기보고와 실제 활동 기록은 별도로 확인할 수 있어야 합니다.
- 반복 클릭·같은 제출 재전송이 고유 목표 충족 수를 계속 올리지 않아야 합니다. 표시 숫자는 서버 근거와 일치해야 합니다.
- 현직자 교류와 학과 이해에 기록이 없으면 미확인으로 표시해야 합니다. 가상 체험을 실제 현직자 교류로 처리하지 않아야 합니다.
- 템플릿 시나리오, AI 미연결, 평가 미연결을 화면에서 구분해야 합니다. 자유 답변이나 제출물의 내용을 채점했다고 표현하지 않아야 합니다.
- 서버 저장 후 목록 갱신만 실패했다면 저장 결과를 유지하고 목록 갱신만 재시도해야 합니다.

## 기존 테스트를 수정할 때

[tests/app.spec.ts](../tests/app.spec.ts)는 이전 체험판 기준이며 이번 작업에서 수정하지 않았습니다. 아래 차이를 반영한 후 사용자가 테스트를 실행해야 합니다.

| 기존 기대 | 개편 후 기준 |
| --- | --- |
| `/`가 학생 홈 | `/`는 소개, 앱은 `/app/`; 소개 원본 비교와 학생 화면 확인을 구분 |
| `/#...`에 바로 활동 입력 | 정규 경로 `/app/#...`, 실제 서버 계정·세션 준비; 옛 경로는 별도 연결 시나리오 |
| localStorage의 활동·초안을 직접 검사 | 인증된 API 또는 화면에서 서버 기록·초안·재접속 복원 확인 |
| 진단·체험 후 고정 점수 기대 | 고유 목표와 서버 근거로 계산한 충족률, 자기보고 제외·미확인 상태 확인 |
| 학생·교사 선택과 가상 학생 배정 | 학생 가입·로그인·소유권 분리로 대체; 교사 경로 제거 |
| AI 자유 답변·완료 문구의 기존 문자열 | 템플릿/AI 미연결 표시와 현재 접근성 이름을 기준으로 갱신 |
| 프론트 개발 서버만 시작 | FastAPI와 격리된 사용자 확인용 DB를 함께 준비 |

기존 `npm.cmd run test:e2e` 명령은 남아 있지만 현재 화면과 계약에 맞게 고치기 전에는 통과를 기대하지 않습니다. 테스트를 수행할 때 개인 사용 DB 대신 별도 `KINGCAREER_DATA_DIR`를 사용하세요.
